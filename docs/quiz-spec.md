## 1. מטרה ומיקום באתר

כלי שיווקי אינטראקטיבי שמייצר לידים איכותיים: בעל העסק מזהה בעצמו איפה הוא מבזבז זמן, מקבל תוצאה אישית, ומשאיר פרטים לסקירה ראשונית בחינם.

### הדף אינו מפורסם

לפי החלטה מפורשת, הדף נגיש **בקישור ישיר בלבד**:

- `robots: { index: false, follow: false }` במטא-דאטה של העמוד.

- **אין** אליו שום קישור מהאתר — לא ב-Header, לא בפוטר, לא בעמוד הבית ולא במאמרים.

הוראות הפרסום בעתיד מתועדות בראש `src/app/(site)/automation-check/page.tsx`.

### ראוט

`/automation-check`

הראוט באנגלית מסיבה טכנית ולא מתוך העדפה: **שם תיקייה עברי בראוטר מפיל את `next build`** עם `InvalidCharacterError` בשלב ה-prerender (נבדק בפועל — הבנייה נכשלה עם `/בדיקת-אוטומציה` ועברה מיד אחרי השינוי לאנגלית). כלל ה-slug העברי של הפרויקט חל על **ערכי `[slug]`** של מאמרים, שהם ערך בזמן ריצה ולא שם תיקייה. ההגבלה תועדה ב-`CLAUDE.md`.

## 2. ביקורת על השאלות והשינויים המוצעים

השאלות בבריף טובות ומכסות את הצירים הנכונים. שלוש הערות:

### 2.1 שאלה 1 (כמה אנשים עובדים בעסק) — לא לתת לה ניקוד

גודל צוות אינו מדד לפוטנציאל אוטומציה: עסק של אדם אחד עם 100 לידים בחודש הוא ליד חזק בדיוק כמו צוות של 10. השאלה נשארת כמו שהיא, אבל משמשת **הקשר בלבד** — לניסוח התובנות ולהבנת העסק לפני השיחה, לא לציון.

### 2.2 שאלה 2 — האפשרות "אין לנו תהליך קבוע של קבלת לידים" מערבבת שני צירים

היא לא מתארת נפח לידים אלא כשל בתהליך. בניקוד היא מטופלת בנפרד (ראו טבלה) ולא כ"אפס לידים".

### 2.3 שתי שאלות חדשות מומלצות

**חדשה — שעות עבודה ידנית בשבוע.** זהו החוסר המשמעותי היחיד בשאלון. בלעדיה אי אפשר לתת תוצאה מספרית מעניינת ("אפשר לחסוך בערך X שעות בחודש"), שהיא הדבר שהופך את מסך התוצאה מציון מופשט להבטחה קונקרטית.

> **בערך כמה זמן בשבוע לוקחת העבודה הידנית והמנהלתית הזו — הקלדות, מעקבים, עדכונים, חיפוש מידע?**
> פחות משעה / 1–3 שעות / 3–8 שעות / יותר מ-8 שעות / לא בדקתי אף פעם

**חדשה — תחום העסק.** מודיעין עסקי מצוין לפני השיחה, ומשמשת פתיחה קלה שמחממת את המשתמש. בחירה מתוך רשימה קצרה: שירותים מקצועיים / קמעונאות ומסחר / בריאות וטיפול / חינוך והדרכה / בנייה ושיפוצים / אירועים / מכירות וטלמרקטינג / אחר. ללא ניקוד.

**סה"כ: 12 שאלות** (10 מהבריף + 2). זמן מילוי ריאלי: 2–3 דקות, בתוך ההבטחה של "5 דקות". אם מעדיפים לקצר — שאלת תחום העסק היא הראשונה שיורדת.

## 3. מנגנון הניקוד

### 3.1 ארכיטקטורה

כל שאלה מנקדת **קטגוריה אחת בלבד** — בלי ספירה כפולה. ציון קטגוריה = `סכום נקודות שנצברו ÷ מקסימום אפשרי × 100`.

| קטגוריה | שאלות | מקס' נקודות |
|---|---|---|
| A · ניהול לידים ומכירות | Q3, Q4, Q8 | 60 |
| B · עבודה ידנית וחזרתית | Q7, Q11 | 40 |
| C · חיבור בין מערכות ומידע | Q6, Q10 | 40 |
| D · ניהול משימות ומעקב | Q5, Q9 | 40 |

הערה: Q6 (העתקת מידע) יכולה להיחשב גם כעבודה ידנית, אבל **הסיבה** שלה היא מערכות מנותקות — ולכן היא בקטגוריה C. זה שומר על מיפוי חד-חד-ערכי.

### 3.3 הציון הכולל

ממוצע משוקלל של ציוני הקטגוריות — **לא** סכום גולמי, כדי שקטגוריה A (3 שאלות) לא תשתלט:

```
total = round(A×0.30 + B×0.30 + C×0.20 + D×0.20)
```

טווח בפועל: 10 (כל התשובות ה"מסודרות" ביותר) עד 100. עסק ממוצע נוחת סביב 50–65.

### 3.4 רמות

| טווח | תווית | ניסוח |
|---|---|---|
| 0–29 | **בסיס מסודר** | "העסק שלך מנוהל מסודר יחסית — יש כמה נקודות נקודתיות שכדאי לבדוק." |
| 30–54 | **פוטנציאל בינוני** | "יש בעסק כמה תהליכים שאפשר לחסוך בהם זמן משמעותי." |
| 55–74 | **פוטנציאל גבוה** | "לפי התשובות שלך, יש בעסק מספר תהליכים שכדאי לבדוק לאוטומציה." |
| 75–100 | **פוטנציאל גבוה מאוד** | "חלק ניכר מהעבודה בעסק נעשה ידנית — כאן יש הכי הרבה מה לחסוך." |

כל רמה, כולל הנמוכה, מקבלת ניסוח חיובי ו-CTA. אף אחד לא מקבל מסך שאומר לו "אין לך מה לחפש כאן".

### 3.5 הערכת שעות — התוצאה האישית

זה מה שהופך את מסך התוצאה למעניין. מבוסס על Q11 ועל הציון הכולל:

```
weeklyHours   = { <1: 0.5, 1–3: 2, 3–8: 5, >8: 10, לא בדקתי: נגזר מ-(B+C)/2 → 2 / 5 / 8 }
automatable   = 0.25 + 0.35 × (total / 100)          // 25%–60%
monthly       = weeklyHours × 4.3 × automatable
טווח מוצג     = round(monthly × 0.8) עד round(monthly × 1.2)
```

מוצג כ: **"בערך 12–18 שעות בחודש"**, תמיד עם הסתייגות גלויה — *"הערכה גסה על סמך התשובות שלך, לא הבטחה"*. אמינות שווה יותר ממספר מנופח, ובעל עסק שמזהה הגזמה מפסיק לקרוא.

אם התוצאה יוצאת מתחת ל-2 שעות בחודש — לא מציגים את המספר בכלל, רק את הציון והתובנות.

## 5. מבנה הנתונים ומוכנות ל-CRM

### 5.1 API

הרחבת `/api/lead` הקיים בוריאנט חדש `"quiz"` במקום ראוט נפרד — כך נשמר כל הצנרת הקיימת (Resend, מייל לבעל העסק, מייל אישור אוטומטי, ולידציה).

### 5.2 Payload

```jsonc
{
  "variant": "quiz",
  "source": "שאלון פוטנציאל אוטומציה",
  "name": "...", "phone": "...", "email": "...", "business": "...",
  "quiz": {
    "version": 1,
    "completedAt": "2026-09-03T12:00:00.000Z",
    "score": {
      "total": 68,
      "band": "high",
      "categories": { "leads": 72, "manual": 65, "systems": 60, "tasks": 70 }
    },
    "estimate": { "weeklyHours": 5, "monthlyLow": 12, "monthlyHigh": 18 },
    "answers": [
      { "id": "leadsPerMonth", "question": "...", "value": "30-100", "label": "30–100", "points": 16 }
    ],
    "freeText": "...",
    "insights": ["leads", "repetition", "scattered"]
  }
}
```

`answers` שומר גם את הערך המכונתי (`value`) וגם את התווית לבני אדם (`label`) — כך אין צורך לפענח קודים בצד ה-CRM.

### 5.3 מייל לבעל העסק

טבלת התשובות המלאה, הציון הכולל, ארבעת ציוני הקטגוריות, התובנות שהוצגו, והטקסט החופשי — כדי שאפשר יהיה להיכנס לשיחה עם תמונה מלאה של העסק.

### 5.4 וובהוק ל-CRM

אם מוגדר משתנה הסביבה `LEAD_WEBHOOK_URL` — הראוט שולח את אותו JSON בדיוק גם לשם, ללא חסימה (`fire-and-forget`; כישלון בוובהוק לא מפיל את הפנייה ולא נראה למשתמש). כך החיבור ל-CRM בעתיד הוא הגדרת משתנה סביבה אחד, בלי שינוי קוד. הוובהוק חל על **כל** הפניות באתר, לא רק על השאלון.

### 5.5 אנליטיקס

GA כבר מחובר בפרויקט. אירועים: `quiz_start`, `quiz_progress` (עם מספר השאלה), `quiz_complete`, `quiz_lead`. מאפשר לראות איפה בדיוק אנשים נוטשים ולשפר את השאלון.

## 6. UX ועיצוב

### 6.1 שפה עיצובית

זהה לחלוטין לקיים באתר — ללא חריגה:

- צבעים: `brand-navy` `#0a2440`, `brand-blue` `#2b93c9`, `brand-cyan` `#6ec9e8`, `brand-offwhite` `#f5fbfe`
- פונט: IBM Plex Sans Hebrew (כבר טעון גלובלית)
- כרטיסים: `rounded-2xl`, `ring-1 ring-brand-navy/[0.07]`, `bg-white/70`, hover עם הרמה קלה — בדיוק כמו `WhatWeDo`
- כפתורים ראשיים: `rounded-full`, `bg-gradient-to-l from-brand-blue to-brand-cyan`, טקסט `brand-navy`
- אנימציות: `motion/react` (כבר תלות בפרויקט), `Reveal`, ורקעים קיימים `TechBackdrop` / `bg-glow`

### 6.2 מסכים

1. **פתיחה** — רקע בהיר, הכותרת וטקסט המשנה מהבריף, כפתור "בואו נבדוק את העסק שלי ←" ושתי הבטחות (`✓ ללא התחייבות` · `✓ לוקח רק כמה דקות`)
2. **שאלה** — כרטיס לבן מרכזי: פס התקדמות דק בגרדיאנט כחול-ציאן, "שאלה 3 מתוך 12", השאלה, כפתורי בחירה גדולים, כפתור "חזרה"
3. **תוצאה** — סקשן כהה (`brand-navy` gradient, כמו סקשן יצירת הקשר) לניגוד דרמטי: מד קשתי, ספירה עולה של המספר, ארבעה פסי קטגוריה שמתמלאים, כרטיסי התובנות, הערכת השעות
4. **טופס** — שם / טלפון / מייל / שם העסק (אופציונלי), כפתור "אני רוצה סקירה בחינם ←"
5. **תודה** — אישור, ותזכורת שהתשובות כבר נשלחו

### 6.3 אינטראקציה

- **מעבר אוטומטי** אחרי בחירה — השהיה של ~250ms עם הבהוב מצב "נבחר", כדי שהבחירה תיראה ולא תרגיש כמו קפיצה. חריג: Q12 (טקסט חופשי) דורש לחיצה על "המשך", עם כפתור "דלג"
- **חזרה** — כפתור בראש הכרטיס; שינוי תשובה קודמת שומר את שאר התשובות
- **מקלדת** — ספרות 1–5 לבחירה, Enter להמשך, Backspace לחזרה
- **אנימציה** — החלקה + עמעום, 220ms, מודעת כיוון (קדימה = נכנס משמאל ב-RTL), מכבדת `prefers-reduced-motion` כמו כל השאר באתר
- **שמירת התקדמות** ב-`localStorage` — רענון דף לא מאבד את התשובות
- **מובייל תחילה** — כפתורי בחירה ברוחב מלא בגובה 56px לפחות, אזור לחיצה נדיב, ללא גלילה אופקית
